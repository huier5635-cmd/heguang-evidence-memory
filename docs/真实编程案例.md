# 真实编程案例：为什么命中率不能当作解题率

## 边界

本轮使用公开 SWEContextBench 的任务描述和固定仓库基线，由当前助手单独开发。没有收费模型 API，也不是 AML 的固定编程 Agent。案例代码和文件仅在 `case-studies/` 中用于学习，生产 wheel 不包含它们，不会按任务编号返回预制答案。

## Requests：基线已通过本地复现

公开任务 `psf__requests-3481` 描述 `stream=True`、`decode_unicode=True` 下的异常。取得固定基线 `b2f6173a3833153f57d9e3baa6728c5cc46c0b29` 后，使用本机 chunked HTTP 服务检查，原代码能返回全部三行，没有修改目标代码。

这不能算“修复成功”。运行的是 Python 3.12，并为旧依赖提供了兼容导入，无法替代原问题的 Python 2.7 环境或正式测试。结果只说明这个本地复现不产生所述错误，不能据此断言整个数据集有误。

报告在 `case-studies/requests-3481/baseline-result.json`，固定来源和摘要在旁边的下载回执中。

## SymPy：首轮失败必须保留

公开任务 `sympy__sympy-27868` 的基线为 `22fc107a94eaabc4f6eb31470b39db65abb7a394`。任务描述中的 `Sqrt[2]*σ` 确实失败；检索第一条找到了早期单个希腊字母修复，其 `isascii()` 分支解释了组合表达式为什么跳过词法分析。

第一轮独立补丁在查看目标测试内容前冻结。5 个可见示例从 3/5 到 5/5，但公开评测的两个 FAIL_TO_PASS 测试仍失败，原有 PASS_TO_PASS 测试通过。**首轮完整任务按失败记录。** `first-attempt-plan.json`、`first-attempt.patch` 和 `first-attempt-evaluation.json` 保留这一事实。

评测器在代码冻结后才读取公开的 `test_patch/FAIL_TO_PASS/PASS_TO_PASS`；这些字段没有进入 Add/Search。目标解答 `patch` 始终没有读取。

## 后续开发修复

首轮结果揭示了更广的要求：组合音标不被 Python 正则的 `\w` 完整接纳，数学字体标识符不宜交给 Python 的名称规范化，还需处理部分 Wolfram 命名字符和常量。

后续在已知公开测试上开发：

- 词法匹配使用等长视图识别组合标记，再按原字符位置恢复名称，保留准确拼写。
- 非 ASCII 名称直接构造 Symbol，避免 Python 标识符转换改变数学字体。
- 加入希腊字母转义、相关标准常量和明确的非法转义错误。

开发修复通过该目标模块的全部三个测试函数，包括两个 FAIL_TO_PASS 和一个 PASS_TO_PASS。它包含很多断言，不是仅测试三个输入。报告与补丁为 `development-result.json`、`development-fix.patch`。

这属于看过公开失败后的开发结果，不是新的盲测成绩，也不证明记忆比无记忆更好。手动案例本身没有无记忆对照。后续独立本地模型对照见下文，不能估算正式解题率。
