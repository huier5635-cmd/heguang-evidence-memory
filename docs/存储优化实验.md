# 存储优化实验：不重复保存全文索引正文

本分支是未上线的存储候选，以公开 v0.1.1 提交 `26a922f02119988d9d891800371c170ba116629c` 为基准。它不改变分块、查询线索、RRF 权重或返回原文。当前运行服务仍使用原版，比赛没有使用此候选，也没有官方成绩。

## 为什么能节省磁盘

原版同时在 `docs` 与两个 FTS5 全文索引的正文影子表里保存文本。候选使用 `content=''`、`contentless_delete=1`，FTS 只维护检索需要的信息，正文从 `docs` 取回。该能力要求 SQLite 3.43 或更新版本。[SQLite 官方说明](https://www.sqlite.org/fts5.html#contentless_delete_tables)

FTS 的整数 rowid 必须稳定对应一条证据。候选给 `docs` 增加显式 `doc_rowid INTEGER PRIMARY KEY`，插入证据后用它写入两张 FTS；检索时联表取原有的文本型 `id`，对外 ID 不变。使用显式主键是因为 `VACUUM` 可能改变没有显式整数主键的表的隐式 rowid。[SQLite VACUUM 说明](https://www.sqlite.org/lang_vacuum.html)

索引签名新增 `fts_schema=2`，必须使用新数据目录；本实验没有提供旧数据库的自动迁移。过期清理先删除相应 FTS rowid，再删除证据和写入记录，清理、VACUUM 和重新打开后继续验证剩余证据。

## 已完成的验证

完整聚合记录见 [fts-candidate-validation.json](../results/fts-candidate-validation.json)。

| 验证 | 观察结果 |
|---|---|
| 原始公开 LoCoMo | 10 个样本，399 次 Add、5,882 条消息、3,011 个证据块；1,973 次 Top-100 Search 完整数组相同 |
| 公开 LoCoMo-Refined | 10 个样本，相同数量写入；1,375 次 Top-100 Search 完整数组相同 |

| 占用 | 两套数据各由 33,476,608 字节降为 21,450,752 字节，均减少约 35.9%，包含数据库与残余 WAL |
| 生命周期 | 混合新旧数据清理、剩余证据、重新打开、重试、清理后新增、中途 FTS 写入失败时事务回滚均通过 |
| 本地测试 | Windows SQLite 3.53.1，19 项通过 |
| 云端测试 | Ubuntu 24.04 SQLite 3.45.1，19 项通过；8 个模块的规范化源码指纹逐一一致 |

本地旧文件与候选文件的换行符不同，因此报告同时记录原始字节指纹与 UTF-8/LF 文本指纹。云端字节指纹与候选的 LF 指纹完全相同。两个应用模块的源码文本有变化：`engine.py` 和 `store.py`；其余应用模块不变。

这些是两个相关公开数据集上的词法行为回归。它们不证明真实模型质量、未见数据的答题准确率、断电恢复或 3 亿 token 正式容量。模型相关测试使用模拟网络；没有调用付费模型、没有消耗官方次数。Dockerfile 增加最低 SQLite 版本构建检查，但本轮未构建 Docker 镜像；云端验证采用实际 Python 环境。

## 怎样复现比较

准备基准源码目录、本候选源码目录和作者发布的公开 LoCoMo JSON。两份源代码各自保留 `aml_memory/`、`tools/public_eval.py`、`tests/` 和 `pyproject.toml`。在已安装运行依赖的 Python 环境中：

```powershell
python tools/compare_storage.py --baseline PATH_TO_BASELINE --candidate PATH_TO_CANDIDATE --dataset PATH_TO_LOCOMO_JSON --dataset PATH_TO_REFINED_JSON --work-dir PATH_TO_FRESH_WORK_DIR --output comparison.json --baseline-label 26a922f02119988d9d891800371c170ba116629c
```

每次选择新的工作目录。工具会复制两份源码、使用独立数据库，只运行 lexical，不需要外部模型权限；输出仅含汇总与指纹，不写逐题原文。首次逐样本写入后，分别查询两份数据库并逐项比较完整结果数组，最后核对 SQLite 完整性与磁盘字节数。不要给这个工具提供赛事私有评测数据。

## 学习练习

1. 对照两版 `Store.commit()`，说明整数内部主键与对外字符串 ID 各解决什么问题。
2. 跟踪 `Store.lexical()` 的联表，解释为什么索引不保存正文仍能返回原文。
3. 阅读混龄清理测试，解释为什么只测试“整库全部过期”不足以发现关联问题。
4. 比较报告中两种源码指纹，区分换行变化与程序逻辑变化。
5. 解释为什么 35.9% 是此数据上的实测，而不是对所有正式数据的空间承诺。

正式采用前还需验证实际部署、压力、模型资源与版本冻结；不能把实验分支直接当作已完成参赛的版本。
