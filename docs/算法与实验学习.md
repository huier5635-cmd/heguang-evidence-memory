# 和光记忆：算法与实验学习

学习版，2026-10-20。对照[公开代码 v0.1.1 固定提交](https://github.com/huier5635-cmd/heguang-evidence-memory/commit/26a922f02119988d9d891800371c170ba116629c)阅读。这里使用的 LoCoMo 诊断是公开数据上的检索代理指标，不是 Agent Memory Challenge 官方 Smoke、Full 或最终排名。项目整体入口与本地运行方法另见[开发与学习手册](./开发与学习手册.md)。

## 1. 一个记忆检索系统究竟在优化什么

赛事把回答交给统一的 Answer 模型，我们能控制的是 `Add` 如何存记忆、`Search` 把哪些**可核对的原始证据**放在前面。一个好检索结果要兼顾三件事：相关证据被找到；重要证据排得靠前；返回的正文短到足以进入 Answer 的输入预算。把整段历史原样塞进 100 个结果里可能使 Top-100“找到了”，但关键语句仍排在很后面。

## 2. Add：为什么用四句窗口

`aml_memory/engine.py` 中的 `documents()` 先给每条消息加来源头，记录会话、消息位置、角色和可用时间。普通短消息按相邻四条发言组成一个证据块；默认每两条向前滑动。例子：六条短发言 `m0…m5` 会产生窗口 `m0–m3`、`m2–m5`、`m4–m5`。窗口可把“我”的身份、前后指代和后续改口保存在同一段证据里。

窗口也有代价：步长 2 比步长 4 写入更多重复文字，占更多磁盘、向量费用和 Answer 输入；单块太长则降低前排证据密度。长消息由 `text.py` 的 `split_spans()` 按原文字符位置分块，带少量重叠，尽量在句号或换行附近分界。重叠用于避免事实恰好被边界切断，不代表允许改写原文。

### 练习 A：手算切块

打开 `engine.py` 的 `documents()` 和 `text.py` 的 `split_spans()`。用 6 条短消息、一条超过 `AML_CHUNK_CHARS` 的长消息，分别设 `AML_WINDOW_STRIDE=2` 与 `4`，列出每个结果的 `start/end` 和来源。再运行 `tests/test_contract.py` 对照。改参数时换新的 `AML_DATA_DIR`，因为数据库索引签名包含分块配置。

## 3. 词法检索：两套索引为何并行

`text.py` 的 `terms()` 将文本标准化，拆分英文、代码标识符；遇到中文时生成相邻二字词。`store.py` 将证据写入 SQLite FTS5 的 `words` 与 `trigrams` 两张全文索引。第一张侧重词项匹配，第二张将词项再拆成连续三字符片段，帮助召回部分词形不完全一致的内容。`store.lexical()` 查询各索引，用 SQLite `bm25()` 给每张索引分别排名。

不能把不同索引的 BM25 原始分值直接相加：两张索引的分词单位不同，分值尺度也不同。代码用 **RRF** 合并“名次”：

```text
最终分数(doc) = Σ [该检索路径权重 / (60 + 该路径中的名次)]
```

这里名次从 1 开始。词项路径权重 1.0，三字符路径权重 0.75；若问题有多选项，把“问题+选项”作为额外检索路径，其权重只有 0.2。这样选项能帮助找到原文，但不能被当成金标答案。

手算示例：证据 A 在词项榜第 1、三字符榜第 10，证据 B 在词项榜第 3、三字符榜第 2。则 A 约为 `1/61 + 0.75/70 = 0.02711`，B 约为 `1/63 + 0.75/62 = 0.02797`，B 略高。实际还会考虑选项、向量和有限证据反馈路径，最终按分数和 ID 稳定排序。

### 练习 B：观察 RRF

在 `engine.py` 找到 `scores[key] += weight / (60 + rank + 1)`。先用纸笔计算上面的 A、B，再构造两条仅有一个关键字差别的本地记忆，查看 `/search` 返回的 `score` 与顺序。尝试关闭反馈 `AML_BRIDGE_WEIGHT=0` 并与默认值比较，记录“改变了什么”，不要只记录“哪个好”。

## 4. 有限证据反馈：为何仍能核验来源

默认设置可从前四条高分原文中提取出现多次的英文专名，再把这些名称与原问题拼在一起做一轮低权重检索（`AML_BRIDGE_WEIGHT=0.15`）。这有助于多跳问题：问题先命中某人，后续原文出现与该人相关的另一个实体。反馈词必须来自已存原始证据，Search 最终仍返回原文，不产出新答案。风险是首次命中错误时会放大错误，所以该路径可关闭并做消融比较。

`engine.search()` 还用 `covered` 去掉已经完全由前面窗口代表的多消息覆盖，避免 Top K 被相邻重叠块占满。单条长消息的不同片段仍保持可选，避免跨片事实被错误抹除。

## 5. 向量与 LLM：可选模型如何接入

`hybrid` 模式在词法候选外加入 1024 维 `text-embedding-v4` 向量相似度结果，仍用 RRF 融合。Search 中的密集召回在 `store.dense_top()` 分批扫描当前用户的向量，维护 Top K；它不一次载入该用户的全部正文。源代码现阶段没有近似向量索引，因此时间会随该用户的向量数增长，需要在真实负载下再测。

`research` 模式还在 Add 中把**本次 Add 的来源原文**按约 16,000 字符切段，调用 `gpt-4o-mini` 提取标签。模型输出的每条标签附带一个原文 `quote`；只有 `quote` 确实是来源段和目标证据块中的连续原文片段，标签才会进入索引。这样可以加入检索同义词，同时限制凭空生成的标签。一次标签调用服务于同一段来源里的多个窗口，**不是**每个重叠检索块都调用一次。`models.py` 限制全局模型并发，失败时返回明确错误，不悄悄改用其它模型。

比赛 FAQ 限定学术榜 Embedding 为 `text-embedding-v4`、LLM 相关组件为 `gpt-4o-mini`；正式 Full 勾选项还写明开源方法在 Add 阶段预期使用 `gpt-4o-mini`。[官方赛事 FAQ](https://agentmemoryleaderboard.ai/competition/) · [评测页面说明](https://agentmemoryleaderboard.ai/api-guide) 当前纯词法模式只适合确切的本地诊断；是否可作为有奖正式版本，需要主办方明确确认。真实模型调用、费用和延迟尚未验证，不能把模拟测试称作真实模型成绩。

### 练习 C：跟踪一个标签

在 `models.py` 找 `source_tags()`，顺着 `quote in source` 的校验，再到 `engine.add()` 查 `quote in doc["text"]`。思考：若模型返回一个意思正确但不是连续原文的改写，会发生什么？若同一个 quote 出现在多个窗口，会发生什么？这能帮助理解“可追溯”与“召回率”之间的取舍。

## 6. 公开数据实验：指标究竟代表什么

公开 LoCoMo-Refined 共 1,382 道题，其中 1,375 道可把标注证据 ID 映射回原始发言。对一道题，设它的所有标注证据集合为 `G`，前 K 个 Search 块覆盖到的发言集合为 `R_K`：

```text
全证据@K = 1，当且仅当 G ⊆ R_K；否则 = 0。
总体全证据@K = 各题取平均。
```

“前 8,000 字符内全证据”把 Search 结果按顺序累加，直到候选正文约 8,000 字符，再检查是否包含全部标注证据。它衡量证据被摆在多靠前的位置，比只看 Top-100 更接近 Answer 的输入效率；但官方截断按 token 计，不按这里的字符计，因此仍只是代理指标。

以下完整回放来自 v0.1.0 固定版本，均是公开数据，不是官方 Full；v0.1.1 另做下文所述的固定小集行为回归：

| 配置 | 全证据@5 | 全证据@100 | 前 8,000 字符全证据 |
| --- | ---: | ---: | ---: |
| 步长 2、反馈开、完整来源头 | 72.87% | 93.89% | 74.25% |
| 步长 4、反馈关、完整来源头 | 71.35% | 95.20% | 72.80% |
| 步长 4、反馈关、紧凑来源头 | 71.49% | 95.05% | 75.85% |

这张表不能证明“紧凑配置绝对最好”：它的前 8,000 字符指标更好，但前 5 条覆盖略低。前两项设置同时变动，无法把效果单独归因于窗口步长或反馈。只有一个公开数据集，并未以完全独立的留出集证明泛化；找到了标注证据，也不代表统一 Answer 一定答对。

本地 v0.1.0→v0.1.1 还对 100 道固定公开题做过词法回归：两版完整 Search 数组 100/100 一致。这个检查说明优化存储读取路径后，这些固定输入的行为没有变，不证明向量/LLM 模式、全量性能或官方得分。

### 练习 D：自己设计可信消融

固定同一公开数据、同一 `top_k` 和同一指标，只改变一个参数；先试 `AML_WINDOW_STRIDE`，再单独试 `AML_COMPACT_HEADERS`。每次使用新的数据库目录和同样的 `user_id` 生成规则，保存配置、代码提交、题目分母、`@5/@100` 与字符预算指标。写结论时至少说出一个该指标无法检验的能力。

## 7. 容量和费用：把“估算”与“实测”分开

官方文本赛道约 3 亿 token。[比赛规模](https://agentmemoryleaderboard.ai/competition/) 如果把所有输入仅向量化一次，按阿里云当前公布的 `text-embedding-v4` 北京实时价格 ¥0.5/百万输入 token，纯算术基线是 `300 × ¥0.5 = ¥150`。[官方模型价格](https://help.aliyun.com/en/model-studio/text-embedding-v4) 真实 Add 会产生窗口重复、来源头、查询、重试，账单可能更高；此数也不含 LLM、服务器和流量。

本地 1,000 次合成 Add（20,000 条合成消息、10,000 个检索块）和 100 次 Top-100 Search 的词法路径结果：Add p50/p95 为 66.6/122.0 毫秒，Search p50/p95 为 445.5/488.2 毫秒，数据库与 WAL 约 138 MB。[聚合记录](../results/synthetic-capacity-lexical.json)保留了测量限制：统计完成后，原进程在 Windows 临时目录清理阶段退出非零；连接清理已修正，但该 1,000 次实验尚未重跑。这些数字只针对本机、合成文本、单一用户和无模型配置，不应外推为 3 亿 token 正式 Full 的性能承诺。

公开 LoCoMo 小样本的 SQLite 占用用于粗略规划：紧凑词法配置按 3–5 字符/token 线性外推可能约 13–22 GB；1024 维向量另可能约 5–8 GB，再加系统、索引日志和备份。数字高度依赖各数据集文本形态，不是正式数据测量。当前试用服务器 30 GB 磁盘，须以真实增长监控决定能否承载 Full。`research` 的 LLM 调用单位是 Add 来源段，**不能**按检索块数估算调用次数；实际请求数、费用和吞吐都待测。

### 练习 E：做自己的容量表

选固定的公开数据，记录原文 token 或字符、Add 次数、证据块数、实际 SQLite+WAL 字节数、p50/p95 延迟。分别计算“每条原文消息多少字节”与“每个证据块多少字节”，再写上为什么两种比例都不能可靠预测其它 32 个数据来源。不要把免费的本地词法耗时当作真实模型 API 的耗时。

## 8. 推荐学习路线

1. 读 `schema.py` 与 `api.py`，用 `tools/preflight.py` 看 API 如何满足比赛契约。
2. 读 `engine.documents()`，完成练习 A，弄清窗口与来源。
3. 读 `text.py`、`store.lexical()`、`engine.search()`，完成练习 B，手算 RRF。
4. 读 `models.py` 与 `store.dense_top()`，完成练习 C，并标出尚未真实验证的路径。
5. 读仓库 `results/` 中的公开结果汇总，完成练习 D、E，学会给每个结论标注数据、配置、分母及限制。
6. 最后看官方 [比赛规则](https://agentmemoryleaderboard.ai/competition/) 和 [API 指南](https://agentmemoryleaderboard.ai/api-guide)，区分我们能控制的检索部分与平台负责的 Answer/Eval。

学习过程中不要把密钥、私有评测样本或用户身份信息写入日志、笔记和公开仓库。
