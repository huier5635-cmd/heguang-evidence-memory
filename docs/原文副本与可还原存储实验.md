# 原文副本与可还原存储实验

本候选版本为 0.1.2.dev4，仍在独立目录开发，未部署或重新提交赛事审核。线上与已提交申请仍是 v0.1.1-lexical-26a922f。源码继承 dev2 的检索索引与 dev3 的可选模型通道；注册、额度、密钥及真实模型调用尚未完成。

## 为什么改

消息原文保存在 messages.content 的 JSON 中，同一文本又保存在 messages.text；检索窗口也同时保存 docs.content 与 docs.text。对于纯文本窗口，后两者只是相同字符的 JSON 表示与普通文本表示。数据库中的多份正文让免费服务器的磁盘更早成为限制。

本轮去掉能够精确还原的冗余副本，保留完整原文、消息角色、时间及会话信息。检索方法、来源窗口、稳定 ID、词项索引和分数计算均未改动；这不是一次召回率优化，也没有使用摘要替代原文。

## 代码怎么读

1. `Store.commit` 继续把每条消息的完整 content 编码为 JSON，写入 messages.content；不再重复写 messages.text。当前服务没有读取该重复列的路径。
2. 检索窗口只有在 content 是字符串并且 text 与其逐字相同的情况下，才将 docs.text 留空。媒体数组或不同的文本呈现仍保留 text。
3. `Store.materialize_doc` 在读取窗口时，还原省去的字符串副本。不能解析或还原为字符串时明确报错，不编造来源。
4. 命中检索和无词项命中的有限回退都经过同一个还原函数。向量扫描仍然只读取 ID 和向量，不加载全文。
5. 索引配置签名新增 storage_schema=3。版本切换必须使用新的 AML_DATA_DIR；本轮没有编写或执行线上迁移。

## 怎样复现

先按 README 安装依赖，在工程根目录运行：

```powershell
.venv/Scripts/python.exe -m pytest tests -q
.venv/Scripts/python.exe tools/compare_storage.py --baseline <v0.1.1源码目录> --candidate . --dataset <公开LoCoMo路径> --dataset <公开Refined路径> --work-dir work/cs4 --output results/compact-public-recheck.json --baseline-label 26a922f02119988d9d891800371c170ba116629c
```

work-dir 必须是不存在的新目录。首次运行使用过长的 Windows 目录，SQLite 主文件路径达到 256 字符，附属 WAL 路径超出当前环境可用范围；可重复得到 SQLITE_CANTOPEN。没有把那次不完整运行计作通过。缩短为 work/cs4 后完整运行成功；旧文件保留在开发工作目录，便于排查。Linux 云端使用独立路径，不涉及这一本地路径问题。

## 验证边界

本地 43 项测试通过，真实模型网络用模拟响应。它们包括新增的 Unicode、引号、换行、媒体与时间字段、不同呈现以及损坏数据处理验证。数据库完整性检查通过。

磁盘节省不代表 Full 容量已通过：还没有正式私有语料、真实 text-embedding-v4 向量、gpt-4o-mini 标签、规定规模的并发 Add 和正式 Answer 成绩。Vercel 路线仍待新服务开通确认，embedding-v4 仍缺资源；不要把替代模型作为指定模型提交。

本轮源文本 28,467,851 字符，共 100 次 Add，最大单次请求 316,281 字节（约 0.30 MiB）；这没有覆盖 64 MiB 请求或多流并发。每阶段唯一标记命中 10/10。健康检查成功 989 次、失败 0 次，P95 8.939 ms。工作进程 RSS 不包含代理、测试控制器、系统与其他服务。
