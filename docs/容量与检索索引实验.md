# 容量诊断与检索索引实验

这份独立开发候选为 **0.1.2.dev2**，基于 `runtime-candidate` 的 `8684fadbadebb0c3183f1c495093a5ac7668a30c`。线上与已提交审核的版本仍是 `v0.1.1-lexical-26a922f`，没有部署此候选，没有运行官方 Smoke 或 Full，也没有真实模型成绩。

## 从真实规模测试发现问题

2026 年 10 月 21 日，在现有的 2 vCPU、1 GiB、Ubuntu 24.04 服务器上，用全新目录和仅监听 `127.0.0.1` 的临时服务，逐档写入 1 千、1 万、5 万、10 万条合成消息。所有 Add、Search 和健康检查走真实 TCP HTTP；模型模式固定为 lexical，使用实际分块、事务、索引和排序代码。

每次 Add 为 1,000 条消息，请求体最大 316,281 字节，约 0.30 MiB。最终有 100 次 Add、100,000 条消息和 50,000 条证据块；原文共 28,467,851 字符。它覆盖了更大的累计规模，不覆盖 64 MiB 单次请求、并发大批写入、真实向量或正式 3 亿 token 数据规模。

旧版在前几档运行正常，但 10 万条时，宽泛查询出现 5 秒以上延迟。查询计划显示两路检索都匹配到 50,000 个候选，按整数主键联查 `docs`，再使用临时 B 树排序。原文表约 196 MiB，需要从较大的表页里取回仅用于排序的 ID。

## 改了什么，为什么能提速

候选增加小索引 `docs_lookup(doc_rowid, id)`，并让词项、三元组检索明确使用它。内部整数主键与对外证据 ID 都在该索引中，候选查询可以从它取到 ID，最后再为有限的入选证据读取正文。覆盖索引的原理见 [SQLite 官方查询规划文档](https://www.sqlite.org/queryplanner.html#_covering_indexes)。

评分仍为原来的 BM25；排序仍为 `bm25(...), docs.id`；候选数量、RRF 权重、并列顺序、分块与返回原文均未改动。查询计划从 `SEARCH docs USING INTEGER PRIMARY KEY` 变为 `SEARCH docs USING COVERING INDEX docs_lookup`，临时排序仍然存在。本轮没有把排序直接换成 `ORDER BY rank`，因为需要保留原有 ID 并列规则；SQLite 对 rank 的一般优化说明见[官方文档](https://www.sqlite.org/fts5.html#sorting_by_auxiliary_function_results)。

先在同一份合成数据库上做 SQL 对照：两张检索表、三类查询、两个 Top-K 边界，共 12 组。每组以 AB/BA 次序交替执行两轮，返回的 ID 和顺序全部一致。宽泛词项查询从约 2 秒降到约 0.1 秒；宽泛三元组查询约从 1.7–2.6 秒降到 0.7–0.8 秒。这是具体样本上的观察，不是通用倍数承诺。

批量建索引时，原文件大小没有增加，是复用了已有空闲页；索引本身占 2,420,736 字节。新库逐批写入时索引占 2,736,128 字节，数据库文件由 397,123,584 增至 399,859,712 字节，约增加 0.69%。不能把文件增长为零理解为索引没有空间成本。

## 完整 HTTP 复测

两版使用同一合成生成器、相同分档、每批 1,000 条、相同配置与查询种子，每档每类各 10 次 Search。表中为脚本计算的 P95，单位毫秒，箭头左为 dev1，右为 dev2：

| 消息数 | 特定标记查询 P95 | 宽泛查询 P95 |
|---:|---:|---:|
| 1,000 | 18.8 → 16.0 | 27.9 → 24.6 |
| 10,000 | 47.9 → 28.0 | 121.4 → 100.2 |
| 50,000 | 129.7 → 99.0 | 544.5 → 450.2 |
| 100,000 | 2595.0 → 228.9 | 5462.9 → 951.3 |

10 万条时，新候选的宽泛查询从约 5.46 秒降为 0.95 秒，特定标记查询从约 2.59 秒降为 0.23 秒。完整探测时间由 190.1 秒降为 115.0 秒，包含写入、查询与核验；不能把总时间差全部算成写入提速。两版每档 10 次特定标记查询均命中合成原文，这不是答题准确率。

| 资源与健康 | dev1 | dev2 |
|---|---:|---:|
| 采样的服务进程 RSS 峰值 | 73.14 MiB | 73.31 MiB |
| 健康检查成功 | 1,604 次 | 939 次 |
| 健康检查错误 | 0 | 0 |
| 健康检查 P95 | 5.333 ms | 5.005 ms |
| 数据库与 WAL 观察峰值 | 409,854,224 字节 | 412,643,912 字节 |

内存由 Linux `/proc` 约每 25 ms 采样，可能漏掉更短的峰值；不包括控制进程、代理、操作系统和其他服务。每档每类只有 10 个延迟样本，脚本采用 lower 分位数定义；单次对照、合成分布和缓存状态都限制结论，不能作为稳定 SLA。两个规模进程均已结束，其临时 HTTP 服务已退出。实验后公网仍为 `0.1.1/lexical`，API、Caddy、清理定时器均 active。

## 保持原检索行为的验证

- 本地 **25 项测试通过**；云端 **25 项测试通过**，15 个上传的应用、测试、配置及测量文件逐字一致。
- 新增测试随机打乱插入顺序，制造相同 BM25 分数，并检查 1、5、400 三种边界及两张检索表，要求完整 ID 顺序与原查询相同，同时核对覆盖索引实际被使用。
- 完整公开 LoCoMo 与 LoCoMo-Refined 共 **3,348 次 Top-100 Search**，相对固定基准 `26a922f02119988d9d891800371c170ba116629c`，每条结果的 ID、原文、顺序与 score 均相同；两份作者数据的指纹也相符。
- 原有保留期、事务失败、重试、重新打开、用户隔离、模型模拟、队列与健康检查回归继续通过。两份公开集相关，结果相同证明这些输入上的回归，不证明真实模型或未见问题的准确率。

本候选版本进入索引签名，使用新数据目录；未提供旧库在线迁移，也没有切换已提交服务。SQLite 仍要求 3.43+。

## 复现和学习

在 Linux 项目环境安装锁定依赖，再以全新工作目录运行：

```bash
python -m pytest tests -q
python tools/scale_probe.py --source . --work-dir /path/to/fresh-synthetic-run
```

工具自行启动 localhost-only lexical 服务，生成合成文本。默认停止阈值为服务 RSS 384 MiB、宿主可用内存低于 192 MiB、单次实验数据库 512 MiB、墙钟 360 秒，并保留至少 2 GiB 宿主磁盘空间。这些是采样停测条件，不是操作系统级绝对配额；只在隔离实验目录运行。

完整测量当时的工具指纹为 `8cd74701c490adf7e9281feeb80a7aae5b7a5eee89a76b1e45e97790a26df2af`，原源码备份见 `results/scale_probe_measured.txt`。当前复现工具额外处理了 WAL 文件在采样间消失、观察器异常和取消时的进程清理。另以 2 秒时限触发停测，2.221 秒结束并确认测试进程已回收；没有因工具保护路径调整重跑全部规模测量。应用代码与上述性能实测保持一致。

建议先对照 `store.py` 的两行索引修改，解释为什么候选阶段只需要 ID；再读新增测试，说明为什么插入顺序不能代替 ID 并列顺序；最后区分 SQL 数组一致、完整 Search 数组一致、合成容量测试和官方成绩四种证据。
