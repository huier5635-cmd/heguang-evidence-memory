# 和光记忆系统：开发与学习手册

版本：2026-10-21 部署记录更新。对应公开代码 [Heguang Evidence Memory v0.1.1 固定提交](https://github.com/huier5635-cmd/heguang-evidence-memory/commit/26a922f02119988d9d891800371c170ba116629c)。开发过程仍在继续；比赛申请、官方 Smoke、Full 和获奖情况应以赛事平台实际记录为准。

## 一、先理解要解决的问题

Agent Memory Challenge 把工作分成两端：我们的程序接收并保存历史消息（`Add`），收到问题时找回相关的**原始记忆证据**（`Search`）；赛事平台用统一的 Answer 和 Eval 流程生成答案并评分。Search 不负责直接作答。第二期的开源方法榜也要求我们自行运行公网 Add/Search API，并公开代码及固定版本。[官方赛事说明](https://agentmemoryleaderboard.ai/competition/) · [API 规范](https://agentmemoryleaderboard.ai/api-guide)

最小工作流：

```text
赛事平台发送一批历史消息
          │
          ▼
       POST /add ──► 校验 ──► 切成带来源的证据块 ──► 写入索引和数据库
                                                        │
赛事平台发送问题                                       │
          │                                             │
          ▼                                             ▼
     POST /search ──► 仅检索该 user_id ──► 排序 ──► 返回原始证据
          │
          ▼
赛事平台统一 Answer / Eval
```

系统的核心原则是“**先保存可追溯的原文，再改进召回**”。存储层为每条检索结果保留写入和会话来源，返回的正文带来源头；不能把模型生成的最终答案伪装成记忆。

## 二、从哪些文件开始读

在公开仓库中按下面顺序阅读，能从入口逐步走到算法：

| 文件 | 阅读时关注什么 |
| --- | --- |
| `README.md` | 项目能做什么、如何运行、哪些工作尚未完成。 |
| `aml_memory/schema.py` | Add/Search 请求的字段和校验条件。 |
| `aml_memory/api.py` | 三个路由（health、add、search），以及鉴权、请求大小限制和并发控制。 |
| `aml_memory/engine.py` | 消息如何变成证据块；检索候选如何融合、排序、去重。 |
| `aml_memory/text.py` | 英文词项、代码标识符和中文二元词的处理；长消息无损分块。 |
| `aml_memory/store.py` | 每位用户一个 SQLite 文件；幂等、原子写入、全文检索、数据到期删除。 |
| `aml_memory/models.py` | 可选的向量模型和 LLM 适配器；默认词法模式不会调用它们。 |
| `aml_memory/config.py`、`.env.example` | 模式、密钥、数据库目录和并发参数。 |
| `tests/`、`tools/preflight.py` | 用测试验证行为和 API 契约。 |
| `manifest.json` | 当前文件指纹、固定模型名、默认模式和正式提交标记。 |

把 `api.py` 想成“接待处”，`engine.py` 想成“记忆处理流程”，`store.py` 想成“仓库”，`models.py` 想成“可插拔的外部服务”。

## 三、跟着一次 Add 读源码

官方输入会提供 `request_id`、`user_id`、`session_id` 和按顺序排列的消息。`schema.py` 先检查字段；`api.py` 检查密钥及请求体大小，调用 `engine.add()`。`engine.py` 根据 `user_id` 加锁，避免同一用户的并发写入与检索互相干扰。

接着 `store.check_write()` 检查幂等性：同一个 `request_id` 加相同请求体可安全重试；同一个 ID 却换了内容会冲突。系统将相邻发言组成四句窗口，或把长消息切成保留原文字符位置的片段。来源、角色、时间随证据保存。`store.commit()` 在同一数据库事务中写入原始消息、证据、索引和写入记录；完成后才回 `success: true`。这符合官方“Add 成功时已持久化并可立即检索”的要求。

阅读练习：在 `engine.py` 找到 `documents()`，用两句短对话和一条长消息手算它会产生多少证据块，再运行 `tests/test_contract.py` 验证。

## 四、跟着一次 Search 读源码

`store.candidates()` 在该用户的数据库上查询两种全文索引：普通词项和字符三元组。字符三元组能减轻拼写形式不同造成的漏检；两组结果通过 Reciprocal Rank Fusion（RRF，按各榜单名次合并）融合。问题选项只作为较低权重的检索线索，不当作正确答案。

`engine.search()` 可从高分证据里的原文专名生成有限的追加检索线索，再为候选排序。相邻证据窗口可能覆盖同一批消息，系统会略过完全重复的多消息覆盖，保留必要上下文。最后只返回最多 `top_k` 条原文证据。正式外部评测 `top_k=100`；返回顺序很关键，因为平台有 Answer 输入长度预算。[官方 API 规范](https://agentmemoryleaderboard.ai/api-guide)

三种配置模式：

| 模式 | 多做了什么 | 当前验证状态 |
| --- | --- | --- |
| `lexical` | 词项 + 字符索引，不调用收费模型。 | 本地契约、公开集诊断和小规模容量测试已做。 |
| `hybrid` | 加入 `text-embedding-v4` 的向量召回。 | 模拟网络测试；真实模型额度和大规模性能待验证。 |
| `research` | 在 Add 中用 `gpt-4o-mini` 提取有原文引用的检索标签，并加入向量召回。 | 模拟网络测试；真实调用、成本和吞吐待验证。 |

公开规则对学术榜的 Embedding 指定 `text-embedding-v4`，对 LLM 组件指定 `gpt-4o-mini`。正式 Full 页面还写了开源方法在 Add 阶段预期使用 `gpt-4o-mini`。纯词法模式能否参评并获奖，需要主办方确认，不能把本地能运行等同于正式资格。[比赛 FAQ](https://agentmemoryleaderboard.ai/competition/) · [正式评测清单](https://agentmemoryleaderboard.ai/api-guide)

## 五、本地动手运行

在仓库目录安装 Python 3.11 或更新版本，然后执行 README 的完整步骤。下面是 PowerShell 的最小示例；随机密钥只放在当前终端环境，不提交到 GitHub。

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.lock
.venv/Scripts/python.exe -m pip install 'pytest>=8,<10'
.venv/Scripts/python.exe -m pip install 'pytest>=8,<10'
$env:AML_API_KEY = .venv/Scripts/python.exe -c "import secrets; print(secrets.token_urlsafe(32))"
$env:AML_MODE = 'lexical'
$env:AML_DATA_DIR = 'data/learning'
.venv/Scripts/python.exe -m uvicorn aml_memory.api:create_app --factory --host 127.0.0.1 --port 8750 --workers 1 --no-access-log
```

另开一个 PowerShell 窗口，先确认 `GET http://127.0.0.1:8750/health` 返回 `status: ok`。若用新终端请求 Add/Search，须先把同一密钥安全地传给新终端；不要把密钥粘贴进截图、公开文档或命令记录。可用 `tools/preflight.py` 按 README 做接口预检，再执行：

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe tools/manifest.py
```

初学时先改一项参数，建立新的 `AML_DATA_DIR`，比较 `/search` 返回顺序；避免把不同索引配置混在同一个数据库。`tests/` 是理解边界行为的好入口：重点看重复 Add、跨用户隔离、长消息、模型失败时的原子性。

## 六、我们怎样检验效果

当前研究报告在[算法与实验学习](./算法与实验学习.md)及仓库的 `results/` 汇总。公开 LoCoMo 和 LoCoMo-Refined 的检验只测“标注的原始证据有没有出现在前 K 个检索结果中”，**不是**官方答题分数。LoCoMo-Refined 上，不同词法配置的全证据 Top-100 覆盖约 93.89%–95.20%，前 8,000 字符覆盖约 72.80%–75.85%；默认配置在 Top-5 指标上更高。配置选择需要同时看前排质量、覆盖和运行成本，不能只挑一列最高值。

另有固定 100 道公开问题的 v0.1.0→v0.1.1 行为回归：两版词法 Search 的结果数组完全相同。18 项本地测试通过。合成的 1,000 次 Add 和 100 次 Search 测试只说明本机小规模路径可运行，不能证明 3 亿 token 的 Full 容量。

建议学习时区分三种证据：**单元测试验证代码边界**，**公开集诊断验证特定数据上的检索代理指标**，**官方 Smoke/Full 才验证赛事接入与最终成绩**。

## 七、上线与参赛的检查顺序

1. 在服务器上运行固定提交，确认数据卷、磁盘、单 worker、密钥和反向代理配置。
2. 从服务器外部访问公网 `/health`，再以独立测试用户调用 Add/Search，核对鉴权、幂等、隔离及返回格式。
3. 核实模型权限、实际额度、预算限制及容量；模型模式做小额真实预检后再宣称可用。
4. 固定代码、配置和公开材料，按[官方申请流程](https://agentmemoryleaderboard.ai/api-guide)提交开源方法榜的文本赛道申请。
5. 收到 Eval Key 后跑官方 Smoke；确认真实容量、资格与版本一致，再发起 Full。
6. 根据私有结果和官方审核跟踪公榜；一等奖只能由官方最终结果确认。

截至本版，阿里云零元试用实例已开通，固定提交已安装，公网 HTTPS 与带密钥合成接口预检通过，独立主机清理任务已启用。学术榜接口审核申请已提交，仍待审核、指定模型资源和赛事 Key；未进行官方 Smoke/Full，也没有官方排名或获奖结果。实例磁盘总量 30 GB，已有估算提示正式 Full 存储可能超过该规格，须用真实增长数据核验，不宜直接承诺全量容量。API 密钥、工作台会话及正式评测数据**不要**写进学习文档或公开仓库。

## 八、术语速查

- **Add**：把原始历史消息写入记忆系统；成功后马上能 Search。
- **Search**：依据问题找出相关历史证据，不代替 Answer。
- **`user_id`**：严格的数据隔离边界；系统按它划分数据库。
- **`session_id`**：同一用户的来源会话标签，不限制用户内跨会话查询。
- **幂等**：同一逻辑写入因网络重试执行多次，最终仍只写入一次。
- **BM25**：按词在文档中出现的情况排序的传统信息检索方法。
- **向量召回**：将文本变成数字向量，用语义相似度补足字面词匹配。
- **RRF**：把多份检索排名合成一份排名的方法。
- **Smoke**：赛事官方的小规模接入测试；通过后才能推进正式 Full。
- **Full**：赛事正式整套评测，分数经审核后才可能上公榜。
