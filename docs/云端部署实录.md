Qianora（千绪）的编程接口已经部署并通过合成接入检查。本记录用于学习部署过程，不是官方成绩。Coding 独立申请仍是草稿，未启动官方 Smoke；Full 仍关闭。文本服务代码、单元文件、环境文件和数据目录不改动。

## 已实际完成的步骤

通过已登录的阿里云命令助手检查伦敦现有 Ubuntu 24.04 实例。Python 3.12.3、SQLite 3.45.1 和 FTS5/contentless_delete 均满足要求。初次可用内存为 346,726,400 字节（约 331 MiB），磁盘剩余 22,620,151,808 字节。原部署草案要求的 700 MiB 内存余量没有满足，不能直接照搬默认服务上限。

文本 `/health` 返回 `{"status":"ok","version":"0.1.2","mode":"lexical"}`。初次内存审计中，文本进程 RSS 约 119 MiB，而 systemd 该服务的 MemoryCurrent 约 260 MiB。二者口径不同，不能把 RSS 当作整个服务的资源占用；控制组还可能统计文件缓存及其他内存。

源码固定为 `978f2ab2bea5ec9f55ce06ce23a31d3e0df4901d`。在独立目录 `/opt/heguang-coding` 中建立新的虚拟环境，下载固定版本的模型。准备任务通过临时 systemd 单元运行，实际应用 MemoryMax=188743680（180 MiB）。任务完成记录核实了 122 个源码文件、依赖检查和全部模型文件校验。准备阶段未启用接口；后面的正式启用步骤另有用户确认和执行记录。

源码 ZIP 的 SHA-256 为 `8247294bc94d545ada378097596f113d7d7ad5b1d0d6282c2d71201d99658c43`。模型仍为已公开材料中的 MiniLM 固定版本，校验值不变。

第一次失败说明 180 MiB 不足；第二次失败只证明 90 秒内未完成，不能推导为再次内存耗尽。第三次保持同一个模型和源码，完成了顺序评分。它不是 16 并发 HTTP 结果，也不能证明官方评测时限和完整规模容量。临时模型单元退出后回收，启动器自身显示的内存不是模型进程峰值。

第二次探测前创建了临时 1 GiB 交换文件 `/var/lib/heguang-coding-host/swapfile`，root 所有、目录 0700、文件 0600。没有修改 `/etc/fstab`，因此不能假定重启后仍自动启用。交换空间不是物理内存扩容，不是 Full 容量证明，也可能增加延迟。

前两次探测结束后，文本健康检查正常。文本 systemd 单元 SHA-256 仍为 `57cd1bc08525d25da36d5a6e4dc00f630918d09d65a076a365d8da63d35298a2`，Caddy 配置仍为 `b335f0e60f8009a11beec741f5b7899e97edcf368f5716f0d54c7a0bb392b181`。

## 官网最低 16 并发的合成接入验证

实际 UI 的 Add 和 Search 并发参数下限均为 16，因此旧草案建议的 1/1 不能直接填写。没有把服务内部处理名额改成 16；在外层保留排队，在受控内存内逐个处理。

执行 `t-gbr70wpadjilj40`，通过现有公网 HTTPS 路由，以 16 个隔离的合成用户同时 Add，再同时 Search。每个用户一条 3,300 字符原文，两个阶段都观测到 16 个重叠客户端。写入 16/16 成功，最慢 0.650 秒；检索 16/16 成功，中位 46.466 秒、最慢 86.435 秒。检索来源区间与原文逐字一致，无跨用户内容。

测试共 87.149 秒；290 次健康检查成功，错误为 0，最慢健康检查 0.284 秒。Coding PID 和自动重启次数未变，文本健康及单元摘要未变。采样 Coding RSS 峰值 253,628,416 字节，控制组 memory.current 采样峰值 257,433,600 字节；主机可用内存最低 80,676 KiB，交换使用峰值 0。二者是采样峰值，不是精确的全生命周期最高值。

这轮验证仅覆盖短合成文本，且排队延迟明显。它不是官方 Smoke，不证明长历史、巨型请求或约 1.8B token 的 Full 容量。官方超时是否适用仍需要真实预检确认。

## 控制台操作经验

命令助手已完成真实命令执行，可靠性高于本次尝试的 Workbench 持续终端。Workbench 新版有功能介绍浮层，且连接多次断开；旧版输入也出现超时，故返回命令助手。操作超时后先查看同一次执行的状态，不能直接重新运行。

正在运行时打开的结果窗口可能保留旧的行和日志；汇总状态改变后，重新打开同一次执行记录读取最终输出。第二次探测的初次日志停在“Running as unit”，最终日志才包含 timeout 和后续文本健康检查。原始记录分别保存，不覆盖成同一份“成功”报告。

为减少重复建表单，建立参数化命令模板，传入经本地审核的非敏感脚本及 SHA-256；服务端核对校验值后执行，记录脚本校验值与退出码。模板仍使用已认证云账号原有权限，不创建 SSH/API 登录凭据。它只供明确授权的开发步骤使用，不能绕过 Full 禁止或其他操作确认。
