# 开发学习文档

## 1. 系统到底做什么

记忆服务接收过去的编程记录，后续按问题找回相关记录。它不执行历史命令，不自动修复当前仓库，也不在 Search 中生成最终答案。平台的编程 Agent 如何使用记忆、能否修复代码，是另一层要单独验证的事情。

例如，历史中有一条 `pytest tests/test_packet.py -q` 命令，下一条工具消息是失败信息。如果只索引 assistant 的 `content`，它可能为空，命令就丢了。实际命令常在 `tool_calls.function.arguments` 或 `extra.actions` 中，完整输出可能在 `extra.raw_output` 中。

对应入口是 `schema.py` 和 `normalize.py`。前者验证消息结构，后者提取可检索视图。原始结构化 JSON 另行保存，便于复核。

## 2. 一次 Add 的过程

```mermaid
flowchart LR
  A[鉴权和请求大小检查] --> B[按用户串行处理]
  B --> C[开始 SQLite 事务]
  C --> D[检查 request_id 与载荷摘要]
  D --> E[恢复本会话的命令身份]
  E --> F[提取命令和工具返回视图]
  F --> G[原文压缩分块和结构化消息归档]
  G --> H[正文 路径 符号索引]
  H --> I[提交事务后同步返回]
```

`request_id` 相同、载荷相同，直接视为成功重试；相同编号配不同载荷，返回 409。任何一步失败都会回滚，避免只存了一半原文或索引。

用户文件名由用户 ID 的 SHA256 生成，不把用户 ID 当文件路径。数据库之间不共享记忆。重复文本只需索引一次，但 `spans` 表保留每一个来源位置。

## 3. 命令为什么不能只靠“上一条消息”配对

工具可能并行调用，记录也可能分成多个 Add。代码使用明确的调用 ID，并限定在相同用户、相同 `session_id` 内查找已经出现的命令。`call_state` 表让这个状态在重启后仍存在。

同一身份在其他回合被重复使用，或者 `actions` 与 `tool_calls` 给出互相矛盾的命令，就不再强行配对。只有原始消息本身继续保留。超过 8,192 字符的命令也不复制进工具输出，防止一个长命令被重复放大；原始长命令不会被截掉。

派生视图会标记 `trajectory_step_v1`，并带父来源 ID。跨 Add 的配对在扩大后的真实公开轨迹测试中验证了 289 组。父来源过期时，较新的输出按自己的保留期继续存在，父链接清空并标记 `paired_parent_expired`；输出中的命令副本随该输出过期。这一点与保留期内的完整原始归档要区分。

## 4. 原文与索引为什么分开存

全文索引适合找记录，不适合当原文档案。`blobs/blocks` 表以固定字符块保存 zlib 压缩的原文及 SHA256；`docs/search` 负责检索；`spans` 连接两者。

Search 只解压命中区间涉及的块，并检查摘要、解压上限和字符长度。返回内容前有一行 `[source {...}]` 元数据，写清来源、会话和字符区间。区间按 Python Unicode 字符计算，不能当成 UTF-8 字节位置。

普通文本的字符区间指向原消息正文。结构化消息的区间指向明确标记的可检索视图；完整原消息保存在 `raw_messages`。两者都可恢复，但不能把派生视图说成逐字等同于原始消息 JSON。

## 5. Search 如何排序

正文先做 Unicode 规范化及代码标识符拆分，例如 `parseHTTPPacket`、`parse_packet` 和其中的组成词。文件路径与符号另开索引，避免正文中的常见词淹没技术线索。

查询时检索三个索引，再做 Reciprocal Rank Fusion：排名越靠前贡献越大。`rarity` 配置会降低过于常见的文件名、符号的影响。返回时删除高度重叠区间，遵守总字符预算，始终保留原文，不用模型改写证据。

`session_penalty` 是已完成消融但默认关闭的研究参数。提高不同历史任务的覆盖面，会挤掉同一任务的后续补丁；在本次开发集上，这个代价大于收益。不能把“更分散”直接当成“更好”。

## 6. 看懂测试

`test_storage.py` 检查原文恢复、用户隔离、幂等、回滚、去重、过期和损坏数据。`test_trajectory.py` 检查命令字段、跨 Add 配对、重启、冲突、跨用户/会话隔离以及父来源过期。`test_api.py` 检查真实协议结构、鉴权和健康检查。

`trajectory_http_probe.py` 会启动一个仅绑定本机的临时 HTTP 服务，每批最多 25 条消息。最新较大样本使用 120 条公开历史轨迹，共 575 次 Add，逐条比对 13,093 条消息；最后关闭并回收自己启动的进程。旧的 24 条轨迹、3,007 条消息报告仍保留为历史记录。

`synthetic_scale_probe.py` 用唯一命令/输出构造大语料；它测试存储和标识符查找，不测试自然语言理解。10 万条消息全部入库，抽样恢复 100 条，做 50 次唯一标识符查询。因此不能写成“10 万条原文逐条验证”，也不能把 100% 标识符命中当成解题正确率。

## 7. 修改代码的建议顺序

先在 `tests/test_trajectory.py` 阅读具体例子，再看 `normalize.py`，然后看 `store.py:add`、`store.py:search`，最后读 HTTP 层。索引的结构、分词或派生视图改变时要换新数据目录；只改返回预算或排序参数可以复用兼容索引。

每次实验保留代码摘要、数据版本、参数和逐题结果。先用开发集定位问题，再用独立仓库验证；封存集要等候选冻结后再开启。已经拿来调参的集合不能继续叫“从未看过的测试集”。

## 8. 目前真正的难点

找到相关历史，并不等于找到可用的修复代码；补丁取回也不等于 Agent 能正确迁移。我们还需要检验大噪声下的证据选择、真实代码解决率、全量数据的磁盘与时间预算，以及云端并发稳定性。优化进程以这些证据推进，不以一次最高检索分数宣布完成。

## 9. 可选重排器如何接入

`heguang_code/reranker.py` 直接对问题和片段配对打分，不生成独立 Embedding 或答案。先取最多 100 条、受内部字符上限约束的检索候选；只对前 16 条评分，每个片段最多三个 token 窗口。融合原始名次和模型名次，再按请求的 top_k 和最终 128,000 字符预算选择完整记录。内部池默认最多 462,400 字符，纯检索模式仍用 32,000 字符最终预算。先套最终字符预算或截 top_k 再重排，会漏掉后面的好片段，接口测试专门检查了这个问题。

模型仅加载固定摘要的本地 ONNX 和 tokenizer。一个共享锁限制同时推理，避免多个请求同时创建大张量。基础服务不需要模型依赖；启用重排才加载这些库。运行服务不使用跨用户查询缓存。

研究版与接口版对 8 个公开开发案例的配对得分差为 0，原文逐条一致；真实 HTTP 公开轨迹测试也已通过。不过这不是完整负载下的模型吞吐或真实解题验证。

扩大预算的实验和代价见 [上下文选择实验](上下文选择实验.md)。[真实编程案例](真实编程案例.md) 保留首轮失败以及后续已知测试上的开发修复，不把两者混成盲测成功。免费生成模型的双组草稿工具仅在 `research/free_codegen.py` 中，不被生产服务导入；具体权限现状见 [资源与对照试验](资源与对照试验.md)。

## 10. 为什么大请求的内存远高于文件大小

收到的字节、JSON 解析出的字符串、规范化摘要中的转义字符串及 UTF-8 编码可能短时同时存在。原版中间件还把接收缓冲保留到了请求处理结束。单看模型本身的内存会漏掉这些峰值。

当前代码提前释放可变请求缓冲，并分段计算写入摘要。摘要合同未改；`test_large_input.py` 验证旧请求摘要仍能幂等重试。超过 16 MiB 或长度未知的请求只允许一份同时处理，排队时不抢小请求的处理名额。错误响应也只返回简短原因和字段位置。原理、数值与限制见 [大请求内存与并发](大请求内存与并发.md)。
