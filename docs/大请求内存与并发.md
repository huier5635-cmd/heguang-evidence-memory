# 大请求内存与并发 · 0.2.0.dev3

## 为什么增加这轮测试

公开轨迹常见批次较小，不能代表接口允许接收的最大载荷。本轮另外构造两份各 60 MiB 的重复代码文本，JSON HTTP 请求各 63,999,418 字节，均低于 64 MiB 接口上限，同时发送给启用重排器的本机服务。

| 阶段 | 采样服务进程树 RSS 峰值 | 两份原文恢复 |
|---|---:|---|
| 0.2.0.dev2 原实现 | 695.15 MiB | 完整 |
| 提前释放缓冲、分段计算摘要 | 618.68 MiB | 完整 |
| 再限制大请求同时处理数量 | 377.11 MiB | 完整 |

数值来自 `results/dev9-large-memory-comparison.json` 及其引用的三个原始报告，最终比首次采样峰值低 45.75%。这是本机 Windows 的采样结果，不能保证其他平台或真实全量语料的内存占用。输入高度重复，主要用于暴露 HTTP/JSON 内存问题，不能代表唯一语料的磁盘规模。

## 修改了什么

中间件接收并检查请求后，立即释放可变缓冲，避免在整个路由执行期间同时保留两份请求字节。写入摘要继续使用原来的规范 JSON 字节合同，只把 UTF-8 编码分成小段更新 SHA256；新旧摘要一致，旧请求仍能幂等重试。

JSON 编码器对单个长字符串仍可能创建较大的转义字符串，这不是常量内存的 JSON 流式存储。接口仍会完整解析获准接收的请求。

大请求准入阈值默认 16 MiB，`HCM_LARGE_BODY_BYTES` 可配置。超过阈值、或没有 Content-Length 的请求，在读取正文前占用唯一的大请求名额。它先等这个名额，再占普通处理名额，所以排队的大请求不会堵住小请求可用的名额。普通处理名额默认仍为 2。

Content-Length 非法或实际长度不符返回 400，超过 64 MiB 返回 413；不会接受后截断正文。合法分块传输仍被支持。健康检查继续绕过处理名额。

回归还发现：框架默认错误响应会回显输入，非法 Unicode 会导致错误响应自身编码失败。现在 422 只返回简短原因与最多 16 个字段位置，既不回显大段源码，也不把永久输入错误变成 500。

## 验证与边界

44 项测试包括旧摘要兼容、非法 Unicode 的稳定 422、错误响应大小、分块输入，以及“大请求排队时小请求仍能完成”。

8 路客户端的公开轨迹验证另外检查正常批次、同步 Add、原文恢复、重试、冲突和跨批次配对。这里的“8 路”是客户端轨迹数量，服务器最多同时处理 2 个请求；不能写成服务器有 8 个处理名额。

现有 1 GiB 云服务器的操作系统和文本服务也需要资源。以上本机证据不替代云端实测；本轮没有改动文本服务或把新候选部署到云端。

复现大请求试验时使用新的目录：

```powershell
.venv/Scripts/python.exe tools/large_payload_probe.py --work C:/aml-runs/large-01 --output results/repro-large.json --model-dir C:/aml-models/minilm --parallel 2 --payload-mib 60 --rss-mib 768 --seconds 120
```

精确复现旧实现需要恢复对应历史源码，不能用新代码重跑后仍叫旧实现结果。源码映射见 `history/report-sources.json`。
