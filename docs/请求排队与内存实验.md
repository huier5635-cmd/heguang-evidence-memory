# 请求排队与内存实验

这份开发候选为 `0.1.2.dev1`，基于尚未上线的 `capacity-candidate`（`db75eaa12053dbc0d264756b27df83b265cef2e5`）。它保留该分支的无正文 FTS5 索引，并修复请求排队时提前缓冲正文的问题。线上和已提交审核的版本仍是 `v0.1.1-lexical-26a922f`。没有调用真实模型，没有执行官方 Smoke 或 Full。

## 问题与修改

原版先读取完整 HTTP 正文，再等待处理名额。假设同时有多个 Add，而模型调用或数据库写入暂时很慢，后来的请求虽然还在排队，其正文已进入 Python 内存。单个请求限制为 64 MiB 并不能限制所有排队请求的累计占用。

候选的执行顺序改为：

1. 健康检查直接通过；其他请求先验证调用密钥。
2. 等待处理名额。
3. 在名额内按块读取正文，同时检查大小限制。
4. 解析请求，完成 Add 或 Search，然后释放名额。

这样，排队请求不会各自占用一份完整的应用层正文缓冲。Uvicorn 在应用尚未读取数据时可以暂停读取已达水位的连接；具体机制见其[官方流量控制说明](https://uvicorn.dev/server-behavior/#read-flow-control)。连接、代理和操作系统仍有自己的缓冲，所以这不等于排队请求完全不占内存。慢上传也会占用名额；实际部署还需测量合适的并发和超时。

修改仅涉及 HTTP 入口和开发版本标识；检索、分块、模型提示、排序权重和对外 Add/Search 结构不变。当前候选沿用存储实验的 SQLite 3.43+ 要求，且版本进入索引签名，因此需要新的数据目录。

## 先复现，再修复

新增的队列回归测试先在原版执行，结果为 **1 项失败、4 项通过**。失败处正是：第一个 Add 占用唯一名额时，第二个请求的上传生成器仍被提前读取。修复后，候选全部 **24 项测试通过**，其中新增 5 项覆盖：

- 排队正文不提前消费，同时健康检查能响应。
- 密钥错误的请求不读取正文，也不等待被占满的名额。
- 没有 Content-Length 的分块上传超过限制返回 413，之后能继续正常写入与检索。
- 取消排队请求后，后续请求仍能取得名额。
- 模拟模型失败返回 503 后，后续请求仍能取得名额。

这轮本地测试过程有一项上游 Starlette 关于 TestClient/httpx 的弃用提示，测试本身通过；并未据此擅自升级依赖。

## 本机真实 HTTP 对照

复现工具会临时启动一个仅监听 `127.0.0.1` 的 Uvicorn，使用真实 TCP HTTP/1.1 上传。第一个合成 Add 被人为保持在处理中，后面排队 6 个请求，每个正文包含 4 MiB 合成文本。处理名额为 1；Add 实现被替换为等待事件，所以没有索引写入和模型请求。

## 复现与学习

安装项目锁定依赖和 pytest，准备基准源码目录。在候选根目录运行：

```powershell
python -m pytest tests -q
python tools/ingress_probe.py --source PATH_TO_BASELINE --output baseline-ingress.json
python tools/ingress_probe.py --output candidate-ingress.json
```

工具只产生合成文本，不接受官方数据集参数。不要对线上地址施压；此工具自行创建本地服务。较大的压力配置需要自行评估本地资源，默认 6 个、每个 4 MiB 即可复现问题。

学习时可以先找到 `api.py` 中的 `async with slots`，解释为什么把它放在读取正文之后无法控制排队内存；再看取消、异常和 413 三种路径如何退出上下文并释放名额。最后区分“并发数受限”“排队正文不提前读取”和“全部数据能在服务器上完成正式评测”这三个不同结论。
